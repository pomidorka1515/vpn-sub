# Async database repository (Step 4)  
  
`AsyncDatabase` is exported by `db`, alongside the synchronous `Database` used by callers awaiting later migration steps. Constructors perform no I/O or scheduling. Call `await start()` and `await close()` on the same event loop. No synchronous repository adapter is needed: every repository operation has a native async implementation. The existing synchronous implementation remains the staging interface for current core, API, bot, script and watcher callers.  
  
The async repository owns one aiosqlite writer, a complete-transaction write lock, and two independently leased readers by default. Connections enable foreign keys, WAL, the configured busy timeout and NORMAL synchronous durability. Readers additionally enforce query-only access. The schema and migrations remain version 4. Registration/code consumption, bonus redemption, registration confirmation/refund, monthly reset and batch accounting retain complete-operation transaction boundaries and existing error translation. SQL cursors are buffered and closed inside helpers.  
  
Nested repository leases are rejected explicitly rather than recursively acquiring locks: compound operations reuse their leased connection. Child tasks must not be awaited from inside a lease if they require that same writer. Transactions must not span network requests. Startup failure closes acquired connections; close rejects new operations and waits for active leases and file work. Repeated close calls await the same cleanup.  
  
Every SQL operation retains a named task until its worker operation and cursor cleanup settle, including repeated caller cancellation. Cancellation before commit rolls back before releasing the writer. Cancellation during commit first establishes its outcome: a completed commit remains committed and cancellation is propagated. Callers must inspect durable state before retrying an interrupted mutation. Rollback failure disposes the connection; the next writer opens a fresh one. SQL errors also dispose the writer conservatively. Reader errors replace the leased reader before returning its slot. No async connection uses thread-local ownership.  
  
Backups use the existing SQLite backup API on a separately opened synchronous connection through a bounded, owned file offload. Manual and scheduled backups share a lock. Scheduling begins only during startup, uses delay-after-completion cadence and bounded retry backoff, and stops during close. Cancellation cannot stop a worker backup; close drains it before completing. Existing atomic publication, per-instance directories and retention are preserved.  
  
Verification covers existing synchronous DB behavior, async user/auth/Telegram/state operations, concurrent registration and bonus redemption, registration rollback/refund, queued-write and commit cancellation, connection disposal after rollback failure, read isolation, shutdown draining, startup unwind and usable backup restore.
